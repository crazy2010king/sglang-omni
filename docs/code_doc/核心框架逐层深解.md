# 第〇部分 整体框架：一张图与五条设计公理

## 0.1 运行时全景

SGLang-Omni 的运行时是一条**多进程、多阶段、异步流水线**。它不是单体引擎，而是把模型执行拆成若干离散阶段（thinker / talker / vocoder / encoder / preprocessing……），每个阶段独立调度，阶段之间用"控制平面 + 数据平面"双通道通信：

```
                HTTP 层（openai_api.py，非本文重点）
                                │  OmniRequest
                                ▼
┌───────────────────────────────────────────────────────────────────┐
│  Coordinator（每 pipeline 一个，运行在主进程 asyncio loop）           │
│  - 请求准入(max_in_flight) / 状态机 / 多终端结果合并 / abort 广播      │
│  - CoordinatorControlPlane:                                        │
│      PUSH→阶段入口   PULL←完成/流事件   PUB→abort 广播               │
└──────┬────────────────────────────────────────────────────────────┘
       │ SubmitMessage(ZMQ PUSH, msgpack)          ▲ CompleteMessage/StreamMessage
       ▼                                           │
┌─────────────────────────── OS 进程边界（spawn，失败域）──────────────┐
│  Stage（IO shell，不碰模型）                                         │
│  - 控制面收发 / DataRef 解引用 / 扇入聚合 / 流路由 / abort / profiler  │
│  ┌───────────── 阶段内两条线程 ─────────────┐                       │
│  │ asyncio loop 线程：Stage.run() 收发消息   │                       │
│  │ scheduler 线程：scheduler.start() 阻塞跑  │   inbox / outbox       │
│  │      ▼                                  │   （线程安全队列）        │
│  │ Scheduler（计算调度，每阶段一个）           │                       │
│  │  - OmniScheduler(AR, 组合 SGLang)         │                       │
│  │  - Simple/Threaded/Streaming/DLLM        │                       │
│  │      ▼ execute(SchedulerOutput)          │                       │
│  │ ModelRunner（模型感知）                    │                       │
│  │  - forward + sample + 异步解码乒乓缓冲      │                       │
│  │  - Thinker/Talker 特化注入                 │                       │
│  └──────────────────────────────────────────┘                       │
│  阶段间数据（大张量）走 CommEngine→CommRouter→Relay：                  │
│    local_object / cuda_ipc / shm / mooncake                         │
└─────────────────────────────────────────────────────────────────────┘
```

**四层职责表**（`core.md` 的分层，附"是否模型感知"）：

| 层 | 类 | 职责 | 模型感知 |
|---|---|---|---|
| 协调层 | `pipeline/coordinator.py::Coordinator` | 请求生命周期、路由到入口、多终端合并、中止广播、admin 聚合 | 否 |
| IO 壳层 | `pipeline/stage/runtime.py::Stage` | ZMQ 控制面、relay 数据面、扇入聚合、流路由、故障隔离 | 否 |
| 调度层 | `scheduling/omni_scheduler.py::OmniScheduler` 等 | 批选择、KV cache 管理、预填充合并、异步解码编排 | 部分 |
| 执行层 | `model_runner/base.py::ModelRunner` 及特化 | 前向、采样、多模态嵌入注入、CUDA Graph | 是 |

## 0.2 五条设计公理

读任何一层之前先记住这五条，后面所有看似复杂的机制都是它们的推论：

1. **以计算为中心的拓扑**。每个阶段的瓶颈不同（thinker 是计算密集，vocoder 是访存密集），所以每个阶段拥有**独立的调度器**，互不共享批策略；Stage 只做 IO，把计算全部委托给 scheduler（`runtime.py` 模块头注释原文："Dispatches all compute to scheduler"）。
2. **控制与数据分离**。小消息（提交、就绪、中止，几百字节）走 ZMQ + msgpack；大张量（隐藏状态、音频帧、KV 页）走 Relay 后端（共享内存 / CUDA IPC / RDMA），控制消息里只携带 `DataRef` 指针。控制面永远不被数据面阻塞。
3. **声明式配置 → 编译 → 运行时**。阶段拓扑属于模型代码（`models/*/config.py`），用户只覆写参数；启动时一次性"编译"成 `LogicalProcessPlan` + `StagePlacementPlan` + `ProcessTopologyPlan`，之后运行时代码**不再重推拓扑、不再校验**（`topology.py` 模块头："Membership is final once this plan exists"）。
4. **统一契约 + 组合优于继承**。所有调度器暴露同一套 `inbox / outbox / start / stop / abort`，Stage 因此无需分支；`OmniScheduler` 不继承 SGLang `Scheduler`，而是用 `__getattr__` 在**类上**查找方法并绑定到自身实例（§3.1 详解）。
5. **失败域 = OS 进程**。同一进程内的多个阶段共享一个 asyncio loop、一个命运（`stage_workers.py::_run_process`："if any stage raises, the whole process exits"）；跨进程只传递数据不传递故障。父进程 5 秒轮询子进程存活，任何死亡 → 协调器失败所有在途请求。

# 第一部分 框架一：配置与拓扑编译

## 1.1 三层抽象与编译流水线

```
PipelineConfig (Pydantic, 声明式)
   │  compile_logical_processes()          config/topology.py
   ▼
LogicalProcessPlan ── 逻辑进程：副本复制的整体单元（membership 最终定案）
   │  expand_replica_stages()             pipeline/replicas.py
   │  build_stage_placement_plan()        config/placement.py
   ▼
StagePlacementPlan ── 阶段 → GPU id(s) + 显存预算
   │  build_process_topology_plan()       config/topology.py
   ▼
ProcessTopologyPlan ── 物理 OS 进程组（非 TP 合组；TP 每 rank 一进程）
   │  allocate_endpoints()                pipeline/runtime_config.py
   ▼
endpoints: ipc://*.sock  +  PipelineRuntimePrep（一次性打包交给 mp_runner）
```

全部发生在 `MultiProcessPipelineRunner.start()` 的第一步 `prepare_pipeline_runtime()` 中（`pipeline/runtime_config.py:115`）。**编译完成后，运行时不再做任何拓扑决策**——这是理解后续所有代码的前提。

## 1.2 LogicalProcess：副本的复制单元

```python
@dataclass(frozen=True)
class LogicalProcess:
    name: str
    stage_names: tuple[str, ...]
    tp_size: int
    num_replicas: int
    replica_devices: tuple[tuple[int, ...], ...] | None   # 每副本一个 rank→GPU 元组
```

关键设计（`topology.py` 模块头）：

- **成员归属在此定案**。`_group_stages_by_process` 按 `stage_process_name(stage)` 分组并保持配置顺序——顺序即进程内的加载顺序，也是显存预算的累加顺序。
- `stage_process_name`（`schema.py`）的规则：**TP 阶段独占进程**（`tp_size>1` 时 process 名缺省为阶段名）；非 TP 阶段必须显式声明 `process`。
- `_resolve_replica_devices` 的校验逻辑（硬核）：声明了 `num_replicas>1` 且含 GPU 阶段的进程**必须**给出 `replica_devices`，数量必须是 `num_replicas × tp_size`，且按副本切片后每副本内 GPU id 唯一。没有 GPU 阶段的进程声明 `replica_devices` 反而报错。

## 1.3 跨进程边的正确性校验：`process_local_edges`

`_pipeline_edges` 收集全部静态交接边（`next` + `stream_to` + `wait_for` 反向边），`_cross_process_edges` 过滤出跨进程的，再与 `type(config).process_local_edges()` 求交集——命中即编译失败。

这条机制存在的理由写在 `Qwen3TTSPipelineConfig.process_local_edges()` 的注释里：

> preprocessing 把准备好的请求存进**模块级** `_PREPROCESSING_CONTEXT/_PREPARED_REQUESTS` 寄存器，AR 引擎 builder 在**进程内**读取。

即：`("preprocessing", "tts_engine")` 这条边的数据**不走线缆**，走进程内全局状态，拆进程会直接静默错乱。编译期把它锁死在"必须同进程"，比运行时崩溃好得多。

## 1.4 GPU 放置与显存预算

`StagePlacementPlanner.build()`（`placement.py`）：

1. 每阶段解析出 `gpu_ids`（标量/int 列表，形状规则在 `StageConfig.model_post_init` 与 placement 侧**双重校验**——注释说明原因：launcher 助手会在构造后改 tp_size/gpu，不能信任构造期检查）；
2. 按 GPU 聚合 `gpu_memory_fraction`，得到 `GpuPlacement.total_gpu_memory_fraction` 与 `missing_fraction_stage_names`；
3. 双重预算校验：
   - 总占比 ≤ `placement.max_total_gpu_memory_fraction_per_gpu`（默认 1.0）；
   - **共置强约束**：一张 GPU 被多个进程组（或副本展开）共享时，每个占卡阶段**必须**声明 `gpu_memory_fraction`（`require_memory_fraction_for_colocation=True`，副本导致的共享无条件要求）。理由在 §5.2：没有预算，共置进程的 KV cache 剖析在数学上不成立。

错误信息会渲染**可编辑的逻辑名**而非展开后的实例名（`_render_missing_fraction_stages`：报 `talker_ar (instance talker_ar@r0)` 而不是 `talker_ar@r0`——因为 YAML 里声明的是逻辑阶段）。

## 1.5 IPC 端点与 Unix socket 路径预算

`allocate_endpoints` 为协调器（completion/abort）与每个阶段（`stage_<name>.sock`、`comm_<name>_rank<N>.sock`）分配 `ipc://` 端点。硬核细节：zmq 的 IPC 路径受 `zmq.IPC_PATH_MAX_LEN`（通常 100 字符）约束，而 runtime 目录名包含 8 位随机后缀。`_truncate_ipc_namespace_prefix` 会**预先计算最长端点后缀**，反推出命名空间前缀的最大长度；算出负数或最小路径已超限时，直接给出"缩短 endpoints.base_path 或阶段名"的可执行错误。这类"把环境限制前置为编译错误"的处理贯穿全代码库。

## 1.6 编译层速查表

| 类型 | 字段 | 角色 |
|---|---|---|
| `LogicalProcess` | stage_names / tp_size / num_replicas / replica_devices | 副本复制单元 |
| `LogicalProcessPlan` | processes / stage_to_process | 逻辑成员定案 |
| `StagePlacement` | gpu_ids / tp_size / total_gpu_memory_fraction | 单阶段占卡 |
| `GpuPlacement` | total_gpu_memory_fraction / missing_fraction_stage_names | 单卡预算账本 |
| `ProcessGroupPlacement` | name / stage_names / gpu_id | 非 TP 进程组（**跨多卡即报错**） |
| `ProcessTopologyPlan` | groups / stage_to_process / tp_stage_to_processes | 最终物理布局 |

# 第二部分 框架二：Coordinator 与 Stage 运行时

## 2.1 协议层：一切消息的形状（`proto/`）

### 状态机与数据模型

```python
class RequestState(Enum):        # proto/request.py
    PENDING / RUNNING / COMPLETED / FAILED / ABORTED
```

`OmniRequest`（用户输入 + params + metadata）与 `StagePayload`（request_id + request + data）是贯穿全线的载荷。一个不起眼但极重要的细节：`StagePayload.prefetched_chunks / prefetched_stream_done` 标注 `init=False, repr=False, compare=False`，且注释明确"**有意不进入 to_dict()**"——它们是调度器本地的流式入口状态，由接收端重建，绝不构成阶段间线上契约。线上契约的最小化从这里开始。

### 消息族与严格校验

全部消息在 `proto/messages.py`，两序列化路径并存：普通 `@dataclass`（msgpack 手动 to/from_dict）与 `msgspec.Struct`（`DataAckMessage`、`DataRef` 等——性能敏感路径）。`DataReadyMessage` 的校验规则值得逐条看（`to_dict`/`from_dict` 双侧对称实现）：

- 流信号（`is_done=True` 或 `error≠None`）**不得**携带 `data_ref` 与 `chunk_id`；
- 数据消息**必须**携带 dict 类型的 `data_ref`；
- `chunk_id` 必须非负 int；`_require_str` 拒绝空串。

这是"线上协议自带卫语句"的写法：坏消息在边界就死，而不是在某个阶段的深处理逻辑里变成谜之 KeyError。`parse_message` 按 `type` 字段分发 13 种消息，未知类型直接 `ValueError`。

### 控制平面消息总表

| 消息 | 方向 | 传输 | 用途 |
|---|---|---|---|
| `SubmitMessage` | 协调器 → 入口阶段 | PUSH/PULL | 投放新请求（携带 `replica_bindings`） |
| `DataReadyMessage` | 阶段 → 阶段 | PUSH/PULL | "数据已写入 relay"，只带 `DataRef` 指针；`chunk_id`/`is_done`/`error` 三态复用 |
| `DataAckMessage` | 阶段 → 阶段 | PUSH/PULL | 接收方消费完成 → 释放发送方 slot/credit（**背压的根基**） |
| `CompleteMessage` | 阶段 → 协调器 | PUSH/PULL | 终态（成功带 result / 失败带 error） |
| `StreamMessage` | 终端阶段 → 协调器 | PUSH/PULL | 部分输出块（音频帧等），带 modality |
| `AbortMessage` | 协调器 → **全体** | PUB/SUB | 按 request_id 广播取消 |
| `AdminMessage/Result` | 双向 | PUSH/PULL | 权重更新/暂停生成等管理操作 |
| `ProfilerStart/Stop` | 协调器 → 阶段 | PUSH/PULL | torch profile 与事件记录 |
| `ShutdownMessage` | 协调器 → 阶段 | PUSH/PULL | 优雅停机 |
| `KVTransferPrepare/Ready` | 阶段(rank) → 阶段(rank) | PUSH/PULL | 分页 KV 传输握手（§4.5） |

## 2.2 ZMQ 控制平面（`pipeline/control_plane.py`）

**socket 形态选择即语义**：

- `PUSH/PULL` 点对点：负载均衡式投递、天然背压（PUSH 满时 send 阻塞/排队）；
- `PUB/SUB` 广播：abort 一发全收。`PubSocket.bind()` 后 **`await asyncio.sleep(0.1)`** 等订阅者连上——经典 ZMQ 慢连接陷阱的显式处理，注释只有一句"Give subscribers time to connect"。

序列化统一 `msgpack.packb(msg.to_dict(), use_bin_type=True)`；`ControlPlaneContext` 是进程级单例 `zmq.asyncio.Context`（重复 `term()` 是 ZMQ 的常见崩溃源，这里集中管理）。

两个门面：

- **`StageControlPlane`**：每阶段三 socket——`PULL(bind)` 收工作、`PUSH` 发完成/流给协调器、`SUB` 收 abort；另持一张 `next_stage → PushSocket` 惰性连接表（`send_to_stage` 用于 DataAck）。
- **`CoordinatorControlPlane`**：`PULL(bind)` 收完成事件、`PUB(bind)` 广播 abort、`stage_name → PushSocket` 惰性表投递 Submit/Admin/Shutdown。

## 2.3 Coordinator：全局唯一的事实来源（`pipeline/coordinator.py`）

### 核心状态（全部 dict，单 loop 访问，无锁）

| 字典 | 键 → 值 | 生命周期 |
|---|---|---|
| `_stages` | 阶段名 → StageInfo（控制端点） | 注册期写入，全程只读 |
| `_requests` | request_id → RequestInfo（状态/当前阶段/终端集） | 提交到完成 |
| `_completion_futures` | request_id → Future | 非流式调用者 await 它 |
| `_stream_queues` | request_id → asyncio.Queue | 流式调用者消费它 |
| `_abort_tasks` | request_id → asyncio.Task | 广播存活期 |
| `_partial_results` | request_id → {逻辑阶段名: result} | 多终端合并暂存 |
| `_admin_ops` | op_id → _AdminPendingOperation | admin 等待期（有 `asyncio.Lock` 保护） |

### 提交路径（`submit` → `_submit_request`）

```
fatal_error 检查 → request_id 保留检查（四处字典任一占用即拒绝）
→ max_in_flight 准入（超限 raise QueueFullError——容量语义：running+queued）
→ 非 OmniRequest 包装为 OmniRequest(inputs=...)
→ assign_replica_bindings(logical_process_plan, RoundRobinBindingPolicy, request_id)
   # 每个多副本 Process 按请求轮询选一个副本号
→ 解析入口实例名（副本拓扑 resolve），未注册即报错
→ 建 RequestInfo(PENDING) + completion future (+ stream queue)
→ 构造 StagePayload{data: {"raw_inputs": inputs}}
→ PUSH SubmitMessage(entry_instance, payload, bindings)
→ 状态置 RUNNING
```

细节：`_request_id_is_reserved` 同时查 `_requests/_completion_futures/_stream_queues/_abort_tasks` 四处——因为 abort 进行中的请求已从 `_requests` 移除但广播任务还活着，此时复用 ID 会让新请求收到旧 abort。

### 完成事件循环（`run_completion_loop`，独占任务消费 PULL）

`_handle_completion` 的完整决策树（硬核）：

1. **未知请求**（已完成/已中止）→ 丢弃并 debug 日志（abort 与完成天然竞态，这里显式吸收）。
2. 副本名归一化：`msg.from_stage` 实例名 → 逻辑名（`replace(msg, from_stage=...)` 重建不可变消息）。
3. **fail-fast**：任何终端失败 → 状态 FAILED、`broadcast_abort`（其余终端阶段可能还在跑！）、清 partials、`_reject_completion_future`。
4. 终端集校验：`from_stage ∉ expected_terminal_stages` → 忽略（`terminal_stages_resolver` 允许**按请求**收窄终端集，如纯文本请求不需要 audio 终端）。
5. **单终端**：立即 resolve——future.set_result / stream queue put，请求移除。
6. **多终端**（如 Qwen3-Omni 的 text + audio）：`_partial_results[rid][逻辑名] = result`；集齐 `expected_terminal_stages` 才 `merged = dict(partials)` 一次性 resolve。部分完成期间 StreamMessage 照常透传给客户端。

### 流式接口的隐藏契约（`stream()` 生成器）

```python
finally:
    # 客户端提前断开（生成器被 close/抛异常退出）时：
    #   → await self.abort(request_id)   广播取消，防止孤儿请求占着 KV
    #   → 清理 stream queue 与 completion future
```

**客户端断开即自动 abort** 是在生成器的 finally 里实现的——这是 HTTP 层断连能传导到 GPU 的关键一跳。

### abort 的三重保护（`abort` / `_run_abort`）

- 广播任务放入 `_abort_tasks`，调用者 `await asyncio.shield(abort_task)`——**调用者被取消，广播仍继续**（注释："a strongly held task keeps local admission closed and lets the broadcast survive caller cancellation"）；
- 广播后立即置 ABORTED、清理 future/queue/requests/partials；
- `_reject_completion_future` 的分流（注释值得背下来）：非流式调用者 await future，用 `set_exception` 传错；流式调用者**从不 await future**（走 queue），用 `cancel` 避免 "Future exception was never retrieved" 噪音。

### admin 聚合

`admin(action, payload, stages, timeout_s)` 生成 `AdminOperation(op_id=uuid4)` 群发到目标阶段（副本拓扑展开、去重保序），future 在 `pending.results ⊇ expected_stages` 时 resolve（`_handle_admin_result`）。权重更新类操作的成功判定**跳过** `skipped/unsupported` 的阶段（`is_update_action`），普通操作则全员成功才算成功。`pause_generation / update_weights_from_disk / init_weights_update_group` 等 RL 工作流端点全是这一机制的薄封装。

## 2.4 Stage：IO 壳层的完整解剖（`pipeline/stage/runtime.py`，全库最大单类）

### 角色与外部 IO 所有权

```python
self._owns_external_io = role in {"single", "leader"}
```

- `single`：普通阶段。**注意**：`single` ≠ 独占进程——声明式拓扑允许多个 single 阶段共享一个 OS 进程（一个 loop），此时它们共享失败域（`runtime.py` 类注释专门强调这点）；
- `leader`/`follower`：TP rank 0 / rank>0。TP 阶段独占进程。follower **没有**外部 IO：收工作走 mp queue（`TPFollowerControlPlane`），发结果只清状态（`_drain_outbox_follower` 中 `stream` 直接丢弃、`error` 直接 raise 杀进程——follower 的错误无法独立上报，随进程死）。

### 主循环与消息分发（`run`）

```python
while self._running:
    msg = await self.control_plane.recv()
    if role == leader and isinstance(msg, (Shutdown|Profiler|Admin)):
        await self._tp_fanout.fanout_control(msg)      # leader 转发给 follower
    if isinstance(msg, ShutdownMessage): break
    if isinstance(msg, TPWorkMessage):                 # follower 从 mp queue 收到的复制工作
        await self._execute(msg.data); continue
    await self._handle_message(msg)                    # Submit/DataAck/DataReady/Profiler/Admin
```

### 接收保序：per-lane 前驱链（最容易被忽略的硬核机制）

`DataReadyMessage` 到达后不是直接 await 处理，而是：

```python
lane = (msg.request_id, msg.from_stage)          # 每条 (请求, 上游) 一条"泳道"
predecessor = self._receive_lane_tails.get(lane) # 上一条同泳道任务的完成 future
completion = loop.create_future()
self._receive_lane_tails[lane] = completion       # 自身成为新尾巴
task = create_task(self._run_receive_task(handler(msg, predecessor), ...))
```

`_run_receive_task` 中 `await coro` 后再 `await predecessor`——同泳道内**后到的任务先等先到的**。为什么必须这样：TCP/ZMQ 不保证应用层处理顺序，而流式块（chunk 0,1,2…）一旦乱序，下游 vocoder 的延迟码流立即损坏。泳道间则完全并行，互不拖累。

### 数据接收三态（`_on_data_ready`）

1. **直通 CUDA IPC payload**（`is_direct_cuda_ipc_payload_ref`）：张量本身就在 IPC 句柄里，反序列化即恢复，**零 relay 参与**；
2. **DataRef + relay**：`comm.read_data` 读回 payload → **先 ack 成功**（释放发送方资源）→ 交给 input_handler；
3. 失败：ack(success=False, error) + `comm.cleanup(request_id)` + 向协调器发 failure。

流式块同理分三态（直通 IPC / inline 内联 / relay），并各自发 `comm_stream_read` 追踪（直通路径绕过了 CommEngine，所以必须自己补发读事件——保持字节计量完整，注释明说）。

### 扇入聚合（`stage/input.py`）

- `DirectInput`：直通，单上游；
- `AggregatedInput(sources, merge, expected_sources_fn)`：`wait_for` 多上游。**动态扇入**是精髓——`expected_sources_fn` 可在首个上游数据到达时按请求内容收窄期望集（如 router 阶段按路由结果决定等谁），但收窄结果被两道闸约束：不得超出静态 `wait_for`、不得为空；收到期望集之外的上游直接 `ValueError`。凑齐才 `merge(inputs)` 返回合并 payload，否则返回 None（继续等）。

### Outbox 排空（计算结果 → 路由）

```python
out = await loop.run_in_executor(None, lambda: outbox.get(timeout=0.1))  # 不阻塞 loop
for batch_index in range(64):          # _OUTBOX_DRAIN_BATCH_SIZE
    ... 路由 ...
    out = outbox.get_nowait()           # 空则收工
```

- 用线程池 + 0.1s 超时轮询阻塞队列，把线程安全 queue 桥接进 asyncio（scheduler 跑在另一条线程）；
- 每排 64 条 `await asyncio.sleep(0)` 让出 loop，防止大 outbox 饿死心跳；
- 三类输出：`result` → `_route_result`；`stream` → 流发送；`error` → `_send_failure`。

### 结果路由决策树（`_route_result` → `_send_to_stage`）

```
get_stream_done_targets(request_id, result)     # 动态解析本请求的流终点，先发 stream_done 信号
get_next(request_id, result)
├─ None（terminal）→ send_complete(CompleteMessage) 给协调器
└─ [targets] → 对每个 target:
   ① target ∈ same_process_targets 且允许 local：
        LocalStageDispatcher.send_payload()        # 进程内直调，零序列化
   ② 含 CUDA 张量 且 target ∈ _direct_cuda_ipc_targets 且未禁用：
        serialize_direct_cuda_ipc_payload()        # 打包存储句柄+事件，单条控制消息
   ③ 否则 CommRouter 选 relay → comm.send_payload()
```

①里的 `allow_local_object` 语义（硬核）：单目标时直接允许本地对象传递；**多目标时不允许**——同一 payload 对象会被多个下游并发消费，可变容器会互踩。唯一例外是 `allow_projected_local_object`：投影器产出的 payload 与原 payload **不共享任何可变容器**时才允许。检查实现在 `_is_isolated_projected_payload` → `_shares_mutable_container`：递归收集原 payload 中所有 dict/list/set/bytearray 的 `id()`，再在投影 payload 里找这些 id。**用对象身份而非相等性判断**——这是防"两个下游共享同一个 dict，一边改了另一边看见"的真·底层处理。

### 流式发送的状态簿记

- `chunk_id` 按 `(request_id, target)` 独立计数；
- 首块发 `_emit_event(stage_first_stream_chunk_sent)`（TTFA 观测锚点）；
- 同进程目标记录进 `_local_stream_targets`，非本地目标记录进 `_nonlocal_stream_targets`——`_can_send_full_payload_locally` 用它回答"这个下游既收 payload 又收流，流能不能也走本地对象"：**payload 走了本地但流走 relay 的混合边，必须整边统一**，否则顺序性被破坏；
- 非内联流块必须 `torch.Tensor`（relay 只搬张量），CPU 张量走 inline（≤16KB 直接进控制消息）或 SHM。

### abort 路径：取消也要有礼貌（`_discard_data`）

`AbortMessage` 广播到达后 `_on_abort` 做：记入 `_aborted`（有界集合，超 10000 裁到 5000——防长寿命服务器无界增长）→ `comm.cleanup` → 清请求状态 → `scheduler.abort`。

但**已经在路上**的 DataReadyMessage 仍会到达（竞态窗口）。`_discard_data` 不做简单丢弃，而是：

- KV_PAGES：ack(success=False, error=aborted)；
- 其他：**照常从 relay 读出数据（drain），再 ack 成功**。

为什么不直接丢弃？SHM/CUDA-IPC 的 slot 是**接收方 ack 后才释放**的（§4.4）。不 drain 不 ack，发送方的 slot 永不归还，credit 耗尽后整条边死锁。取消语义必须自己清理资源——这是系统编程的老规矩。

### 调度器线程与崩溃传导

```python
scheduler_thread = threading.Thread(target=_run_scheduler, daemon=True)
# 线程内：绑 active_stage → set_device(gpu_id) → scheduler.start()（阻塞主循环）
# 崩溃 → asyncio.run_coroutine_threadsafe(self._handle_scheduler_crash(exc), loop)
```

`_handle_scheduler_crash`：对**所有未中止的活跃请求**发 `scheduler.abort` + `_send_failure("scheduler crashed: ...")`，然后关闭控制面。请求不会因调度器死亡而悬挂。stop() 时 join 调度器线程（5s 超时，注释解释：MPS 校验阶段要读线程 finally 里发的终态事件文件，所以必须等，但慢线程只告警不致命）。

`_on_background_task_done` 是所有后台任务（abort listener / outbox drain / comm 任务）的统一回调：捕获异常 → 存入 `_background_task_error` → `_running=False` → 关控制面；`run()` 退出时再抛出——后台崩溃不会静默吞掉，也不会立即炸 loop 中断正在处理的请求。

# 第三部分 框架三：调度器族

所有调度器实现同一公开契约（`OmniScheduler` 类注释原文）：

```
inbox, outbox, start(), stop(), abort(request_id)
```

Stage 只认这个契约。inbox/outbox 是**线程安全** `queue.Queue`（调度器跑在独立线程，Stage 的 asyncio loop 跨线程投递/排空）。

| 调度器 | 适用 | 关键机制 |
|---|---|---|
| `OmniScheduler` | AR 模型（thinker/talker/tts_engine…） | 组合 SGLang Scheduler、KV cache、异步解码、预填充合并 |
| `SimpleScheduler` | 无状态函数阶段（预处理/编码器） | 串行或线程池并发、动态批 |
| `ThreadedSimpleScheduler` | 同上，需并发 | `max_concurrency` 个 worker 协程 + `asyncio.to_thread` |
| `StreamingSimpleScheduler` | 流式消费阶段（vocoder/code2wav） | 流式生命周期钩子 + chunk 批处理 |
| `DLLMScheduler` | 扩散 LM（LLaDA2） | 迭代去噪循环 |

## 3.1 OmniScheduler：用组合而非继承驯服 SGLang

### 3.1.1 `__getattr__` 委派——全库最精妙的兼容手法

```python
def __getattr__(self, name: str):
    try:
        attr = getattr(_Upstream, name)        # _Upstream = sglang.srt.managers.scheduler.Scheduler（类，非实例）
    except AttributeError:
        raise AttributeError(...) from None
    if callable(attr):
        return types.MethodType(attr, self)    # 把未绑定方法绑到本实例
    return attr
```

工作机制：

- SGLang 的 `Scheduler` 是"上帝类"：批选择、KV 管理、重 retract、指标全在里面，且方法直接读写 `self.waiting_queue / self.running_batch / self.req_to_token_pool / self.tree_cache`……
- 继承会被上游重构绑死；拷贝会漂移。
- **组合 + 动态绑定**：OmniScheduler 在自己的 `__init__` 里摆出与上游同名的状态（`waiting_queue`、`running_batch`、`tree_cache`、`req_to_token_pool`、`token_to_kv_pool_allocator`……），于是上游类的方法 `getattr(_Upstream, "get_next_batch_to_run")` 拿到的是**未绑定函数**，`types.MethodType(attr, self)` 绑定后，函数体内的 `self.xxx` 读到的全是 OmniScheduler 摆好的状态。
- **覆写优先**：实例/类字典里已有的属性（`recv_requests`、`run_batch`、`process_input_requests`、`send_to_tokenizer` 等被覆写的方法）不会走到 `__getattr__`——Python 属性查找顺序保证覆写生效。

配套的桥接补丁：

- `_init_parallel_state`：从 tp_worker 取进程组、算 DP-attention 世界信息，并构造上游期望的 `ParallelState` 容器（`_refresh_upstream_parallel_state`）；
- `self_check_during_idle/busy`、`_NoOpGrammarManager`、`_NoOpSender`：把上游依赖的外设替换为 no-op；
- `_UpstreamAbortSender.send_output`：把上游内部的中止通知转成阶段输出。

### 3.1.2 请求进入：inbox → 构建 → 准入 → waiting_queue

`recv_requests`（覆写上游）从本地 inbox 拉消息（TP>1 时仅 entry rank 拉取再 `broadcast_pyobj` 给 followers），分三类：`new_request` 进构建管线、`stream_chunk/stream_done` 转内部处理。构建管线（`_stage_request_build_payloads` 等）：

- `request_builder`（模型特有，如 `preprocess_qwen3_tts_payload` 的产物适配）在**线程池**执行（`request_build_max_workers`），与 GPU 调度解耦；
- **TP>1 时线程池强制降为 1**，注释给出精确理由："preserve identical request admission order on every TP rank"——多线程构建会让各 rank 的准入顺序抖动，NCCL 集合通信立即死锁；
- 构建结果经 `_admit_or_defer_built_request` 做容量检查（`_request_kv_capacity_error` 预检 KV 余量），可延迟（deferred）等待资源；
- `_enqueue_built_request` 入 `waiting_queue`，并打 `_coalesce_enqueue_t` 时间戳（供合并门用）。

### 3.1.3 预填充合并门（`get_new_batch_prefill` 覆写）

目标：让多个小预填充凑一批再进 GPU，摊薄固定步开销。判序（逐级短路，全部命中才放行上游）：

```
prefill_coalesce_requests <= 1 或存在 chunked_req        → 直接放行
decode 空闲且未开 when_idle                              → 直接放行
requires_pending_builds 且无构建在途                     → 直接放行
waiting 为空 或 已凑够 coalesce_requests 个              → 直接放行
最老请求已等满 prefill_coalesce_wait_s                   → 直接放行（饿死保护）
否则 → NextBatchPlan(batch_to_run=None)                  # 本轮扣住不放
```

两个硬核约束：

- **deadline 用最老请求时间戳而非队列头**："the oldest-request deadline survives partial admission and aborts"——部分准入后队列头变了，但更老的请求的等待时长不能被重置；
- **TP>1 直接禁用合并**："the wait deadline reads each rank's local clock, so ranks could disagree on expiry and break lockstep scheduling"——各 rank 时钟不一致会导致一个 rank 放行另一个 rank 扣住，集合通信死锁。

### 3.1.4 批执行：同步与异步双路径

```python
def run_batch(self, batch, ...):
    try: return self._run_batch(batch, ...)
    except Exception as exc:
        self._handle_batch_failure(batch, exc)      # 逐请求发错误，返回 _FAILED_BATCH_RESULT
        return _FAILED_BATCH_RESULT
```

**同步路径** `_run_batch`：`_build_sched_output`（把 ScheduleBatch 包成 `SchedulerOutput(requests=[SchedulerRequest(rid, data=req._omni_data)], batch_data=batch)`）→ `model_runner.execute()` → `_emit_stream_output` → `_make_batch_result` 伪装成上游 `GenerationBatchResult` 交回 `process_batch_result`。

`_make_batch_result` 里的一行关键选择：

```python
next_token_ids = mr_output.next_token_ids
if mr_output.host_token_ids is not None:
    next_token_ids = mr_output.host_token_ids   # 上游 mixin 的 .tolist() 变成纯主机读
```

——直接消费 ModelRunner 已暂存到**固定内存**的 host 副本，避免上游 `.tolist()` 触发阻塞式 pageable D2H（§5.3 详述）。

**异步路径**（enable_async_decode）：`_run_batch_launch` 构建 + `execute_launch`（入队不等待）返回 `_PendingStep`；下一轮迭代里 `_run_batch_resolve` 消费上一步。launch-first 让两步在飞。**与 `enable_overlap` 互斥**，构造时直接 raise，注释给出根因："the async loop would run a batch-result processor built for the overlap contract and leak KV for finished requests"——两条机制管理同样的批结果生命周期，混用必然漏 KV。

**流式发射的 skip_rids 纪律**（`_emit_stream_output` 注释，硬核）：

> "`skip_rids` suppresses emission for requests already finished in an earlier step (the lookahead overrun) — emitting their extra chunk would corrupt the downstream vocoder's delayed-code stream."

异步解码下，第 N 步 resolve 时请求可能已在第 N-1 步判定完成（lookahead 超跑），此时它第 N 步的输出块**必须压制**——多发的音频块会让 vocoder 的增量解码状态错位。中止请求同理：abort 落在步中间时不能再多发一块。

### 3.1.5 abort（`abort(request_id, defer_running_cleanup=True)`）

顺序即正确性（全程持 `_request_admission_lock`）：

1. 记入有界 `_aborted_request_ids`（超限按 FIFO 裁剪，"so a still-quiescing abort survives"）；
2. `defer_running_cleanup=True` 时只**标记**运行中请求（等 stream_output 自然回收 KV），否则立即清理；
3. 取消在途构建 future、剔除 deferred/backlog/waiting_queue 里的请求（`_detach_request_data` 断开数据引用）；
4. 回调 abort_callback（模型侧清理，如 Qwen3-TTS 的预处理寄存器）；
5. **先发终态事件再丢弃状态**（注释：一个永不走到 stream_output 的运行中 abort 曾把 rid 永久留在 `_prefill_start_done` 里，长期运行无界增长还吞掉后续同名请求的 prefill_start）；
6. `_drain_inbox_for_request`：把 inbox 里该请求的迟到消息清掉。

## 3.2 SimpleScheduler：小而完备

单线程循环：`inbox.get(timeout=0.1)` → `_collect_batch`（凑批）→ 计算 → outbox。

- **凑批**：`batch_compute_fn` 存在且 `max_batch_size>1` 才凑。收集循环里非 `new_request` 的消息（流块等）塞进 `_pending_messages` deque 保证不丢不乱；cost 函数超预算时把消息**塞回队头**（`appendleft`）保序；deadline 只在 `batch_wait_when_idle` 时启动，且首个凑到的消息会**重置** deadline。
- **双模式**：`max_concurrency=1` 走串行（内部 `asyncio.new_event_loop` 跑同步/协程 compute_fn）；`>1` 走并发——注意与 batch 模式**互斥**（构造期 raise）。并发模式结构：bridge 协程把阻塞 inbox 桥接成 asyncio.Queue，N 个 worker 协程用 `asyncio.to_thread` 执行同步 compute_fn（同步函数不卡 loop），结果回 outbox。
- **错误合约**：批处理失败时，对批内每个未被 abort 的请求逐个 `_emit_error`——一个请求的失败不吞掉同批其他请求的结果。
- **abort 的延迟消费模式**：`abort()` 只把 ID 记入 `_aborted`（有界 10000→5000）；计算**前后**各做一次 `_consume_if_aborted`（消费即清理 + 回调 abort_callback）——消息可能已在线程里跑，事后拦截。

## 3.3 StreamingSimpleScheduler：有状态流的生命周期

为"同一阶段既要 `new_request` 又要增量 `stream_chunk`，且 `stream_done` 可能先于最终 payload 到达"的阶段设计（vocoder 是典型）。要点：

- **钩子族**：`is_streaming_payload`（区分流式/非流式）、`on_streaming_new_request`（建会话/槽位）、`on_stream_chunk`（增量处理，返回要发射的消息）、`on_stream_done`、`clear_stream_state`（中止/完成后清理）。子类如 `Qwen3TTSStreamingVocoderScheduler`、`MossTTSLocalStreamingVocoderScheduler` 在钩子里管理持久解码会话（延迟码流、滑动左上下文）。
- **类级开关**：`_can_batch_stream_chunks` / `_stream_chunk_batch_max` / `_stream_chunk_batch_distinct_requests` 控制是否把多请求的流块凑批（凑批路径走 `on_stream_chunk_batch`，子类自管锁）。
- **状态簿记**：`_pending_done` 记录"done 先到"的请求；`_stream_payloads` 暂存非流式 payload 等 done 汇合；abort 清 `_aborted_request_ids` + `clear_stream_state`，迟到块按 ID 静默丢弃。

# 第四部分 框架四：双平面通信

## 4.1 四层分解

```
Stage（路由语义：发到哪个阶段、走哪条边）
  └─ CommEngine（字节搬运机制：发送队列、ack、pending、KV 传输）
       └─ CommRouter（局部性分类：这条边用什么 transport + 持有 Relay 实例）
            └─ Relay（物理传输：shm / cuda_ipc / mooncake / …）
```

职责边界由 `CommEngine` 类注释钉死："Stages keep routing semantics; the engine owns byte movement mechanics."

## 4.2 CommRouter：一条边一个 transport（`comm/router.py`）

决策树（`outbound` / `outbound_payload` / `outbound_stream`）：

```
target ∈ same_process_targets        → LOCAL_OBJECT（无 relay，进程内直调）
target ∈ remote_stage_names          → MOONCAKE（跨节点）
self 有 GPU 且 target 是 GPU 阶段     → 平台选择的 intra-node transport：
                                        CUDA_IPC？→ 再验 P2P 可达（_cuda_ipc_peer_available），
                                                    不可达 → SHM + 一次性 fallback 警告
其余（CPU 数据 / CPU 阶段）           → SHM
```

硬核细节：

1. **P2P 探测**：`torch.cuda.can_device_access_peer(target_local, source_local)`，结果按 target 缓存（`_cuda_ipc_peer_cache`）；探测前先确认本进程 GPU 视图未被重映射（`CUDA_VISIBLE_DEVICES` 窗口内），超出可视范围直接 fallback；fallback 警告按 `(stage, target, src_gpu, dst_gpu, reason)` 去重——每条边只警告一次，不刷屏。
2. **直通目标集** `_direct_cuda_ipc_targets` 的推导：`stage_gpu_ids[name] == (placement_gpu_id,)` 且自身也在同一 GPU、且不同进程、非远程。含义：**同 GPU 跨进程**的最短路径——不需要中继池拷贝，直接交换 IPC 句柄让对端 map 自己的显存（`can_use_direct_cuda_ipc` + `payload_has_cuda_tensor` 时走 `serialize_direct_cuda_ipc_payload`，见 §2.4 决策树 ②）。
3. **设备一致性卫语句**：`outbound_payload` 递归收集 payload 内全部张量的设备集合——混合设备（一半 CUDA 一半 CPU）直接 `ValueError`；空集合或纯 CPU → SHM。传错设备的数据在发送端就死，不进 relay。
4. **transport 变更追踪**：`note_transport_choice` 只在"首次选择"与"变更时"发 `comm_transport_selected` 事件（每次传输都发会淹没日志；但边中途换 transport 本身是健康信号，必须记下）。

## 4.3 DataRef：数据平面的统一指针（`comm/data_ref.py`）

`DataReadyMessage` 不带数据，只带一个 frozen `msgspec.Struct`：

```python
DataRef(
    version=1,                       # 前向兼容的协议版本，from_dict 强校验
    kind=DataKind.STAGE_PAYLOAD,     # stage_payload / stream_chunk / kv_pages / weight_bucket / ...
    object_id="...",                 # ack 与 cleanup 的对账键
    transport=TransportKind.CUDA_IPC,
    layout=DataLayout.PACKED_TENSORS,
    buffer=BackendRef(transport, info, length),   # relay 自己的 transfer_info（如 shm_name/size）
    tensors=(TensorMeta(path, shape, dtype, device, offset, size), ...),
    metadata=..., metadata_tensors=(MetadataTensorRef(path, nested DataRef), ...),
)
```

要点：`TensorMeta` 让接收端能**按 dtype/对齐重建视图**；`metadata_tensors` 允许元数据本身也引用一个二级 DataRef（如直通 IPC 流块的元数据张量）；所有 from_dict 做严格类型检查（`_required` 用 `type(x) is not T`，不接受子类/bool 冒充 int）。

## 4.4 Relay 后端

### Relay 抽象（`relay/base.py`）

```python
class Relay(ABC):
    async def put_async(tensor, request_id, dst_rank, receiver_id) -> RelayOperation
    async def get_async(metadata, dest_tensor, request_id) -> RelayOperation
    def cleanup(request_id); def close()
```

`RelayOperation.wait_for_completion()` 是发送方的完成语义；`mark_receiver_done/failed` 是接收方 ack 的回写通道。`create_relay` 工厂按注册名实例化并用 `inspect.signature` **过滤 kwargs**——上层可以无脑传全量配置，各后端只取自己认识的参数。

### ShmRelay：同节点 CPU 传输（`relay/shm.py`）

```
put_async:  semaphore(credits).acquire()                 # 并发上限 = credits
            SharedMemory(create=True, size=tensor.nbytes)
            numpy view 零转换拷入
            sender 立即 close() 自己的映射（句柄交接给名字）
            返回 ShmPutOperation{shm_name, size}
get_async:  SharedMemory(name) 映射 → uint8 视图 → copy_ 到 dest → close → unlink
完成语义:   ShmPutOperation.wait_for_completion 等接收方 mark_receiver_done
            → release_cb（归还 semaphore）
            超时/异常 → _unlink_if_present()（防止泄漏 /dev/shm 段）
```

两个细节见真功夫：发送方 `put` 后**立即 close** 自己的映射（不再需要，早释放）；**接收方负责 unlink**（POSIX 共内存的名字只有在无人映射后 unlink 才安全）。credit 与 ack 联动 = 天然背压：接收方不消费，发送方 acquire 不到信号量。

### CudaIpcRelay：GPU 池 + 事件句柄（`relay/cuda_ipc.py`，全库最硬核的传输实现）

**内存模型**：每进程在指定 GPU 上预分配一整块 `uint8` 字节池（默认 `slot_size_kb=64`，池大小缺省 `slot_size_mb × credits` = 512MB×2 = 1GB → 16384 个 slot）。池**只分配一次**（`_ensure_local_pool`）。

**发送（`put_async`）**：

```
tensor.contiguous().view(uint8).reshape(-1)          # 强制连续 + 字节视图
num_slots = ceil(size / slot_size)
allocation = await _acquire_slots(allocator, num_slots)   # 连续 slot 分配
pool_tensor[offset:offset+size].copy_(flat, non_blocking=True)   # 异步 D2D 拷入池
ready_event = torch.cuda.Event(interprocess=True); ready_event.record(stream)
metadata = {transfer_info: {size, offset, slot_index, num_slots},
            cuda_ipc: {pool_id, pool_storage(句柄), src_device_id, ready_event(ipc_handle)}}
```

- `_ContiguousSlotAllocator`：**连续** slot 分配（`_find_contiguous_with_layout`），不是零散 slot——大张量必须占一段连续池区，碎片化管理内置；
- `pool_storage_handle` 按 **receiver** 缓存：PyTorch 的 CUDA storage export 自带"每导出一个消费者引用计数 token"（注释原话），同一池对同一接收方只导出一次并复用——导出是有限资源；
- `_acquire_slots` 与 relay 失败事件 `asyncio.wait(FIRST_COMPLETED)` 竞速：relay 挂了立刻失败而不是挂死在队列上，且失败时**归还已获 slot**。

**接收（`get_async`）**：

```
pool = _get_remote_pool(metadata)          # _load_cuda_storage_handle 导入对端池（每 pool_id 缓存一次）
_ensure_peer_access(src_device, dst_device)  # P2P 使能，失败即错
pool_slice = remote_pool[offset:offset+size]
dest.copy_(pool_slice, non_blocking=True)  # P2P 直接读对端显存
wait ready_event                            # 等发送方的"数据就绪"事件
```

**事件等待不卡 loop**：`_wait_for_cuda_event` 先 `event.query()` 快路径，未就绪则 `loop.run_in_executor(wait_executor, event.synchronize)`——专用线程池（默认 8 线程，`SGLANG_OMNI_CUDA_IPC_WAIT_THREADS` 可调）让 asyncio loop 继续跑。更硬核的是 `finish_on_interrupt=True` 路径：协程被取消/超时后，**先 `await asyncio.shield(wait_future)` 等内核停止再传播异常**——"A launched GPU copy cannot be cancelled. Keep its resources alive until the kernel stops touching them"。发起的 GPU 拷贝不可取消，这是与硬件语义对齐的资源管理。

**失败传播**：任一操作失败置 `_failed_error` + `_failed_event`，后续所有 put/get 第一时间 `_raise_if_failed`——半死的 relay 不允许继续使用。

### 内联与直通（`comm/stage_io.py`）

- `serialize_inline_stream_chunk`：≤16KB 的块直接 pickle 进控制消息（`InlineStreamChunk` ref），省一整次 relay 往返——小音频帧不值得开共享内存；
- `serialize_direct_cuda_ipc_payload`：把 StagePayload 内**所有 CUDA 张量**连同嵌套容器提取、打包成单个二进制结构 + 存储句柄 + 事件（`TorchCudaIpcPayload`），一条控制消息完成整个 payload 的跨进程传递；
- `extract_tensors`/`restore_tensors`：递归地把任意嵌套结构里的张量替换为 `_tensor_placeholder` 占位符（带路径），接收端按原结构回填——**对象结构走 msgpack，张量本体走 relay**，两平面在此合流。

## 4.5 CommEngine：字节搬运的执行体（`comm/engine.py`）

- **per-target 发送队列**：`_send_queues[to_stage]`，每个目标一个 `asyncio.Queue`（默认 1024）+ 一个 worker 协程。同一目标的所有发送**串行化**（保序），不同目标并行。`send_payload/send_stream_chunk` 只是入队并 `await ready future`，DataRef 由 worker 真正发送后回填。
- **ack 驱动的资源回收**：`ack_transfer(msg)` 按 `object_id` 找到 `_PendingTransfer`，成功 → `mark_receiver_done`（触发发送方 RelayOperation 完成 + slot 归还），失败 → `mark_receiver_failed` + cleanup。`ack_timeout_s` 默认 30s。
- **分页 KV 传输**（`send_kv_pages`）专用握手：先发 `KVTransferPrepareMessage`（声明源页号/池布局）到对端 rank 的专属 socket，等待 `KVTransferReadyMessage`（对端 `prepare_kv_destination` 预留好目标空间）→ 才 `relay.put_kv_pages`。约束硬性：目前仅支持 cuda_ipc、TP 尺寸必须一致、每 rank 只搬到对端同 rank。
- **abort 清算**：`cleanup(request_id)` 通知所有 relay 丢弃该请求的在途对象；失败的 pending KV transfer 被刻意**保留**到进程退出（`_retained_pending_kv_transfers`，"Failed pending KV transfers stay pinned until this dying process exits"——页可能仍被内核 DMA 触碰，提前释放是 use-after-free）。

## 4.6 TP 控制：leader 复制工作给 follower（`pipeline/tp_control.py`）

- `TPLeaderFanout`（leader 侧）：`fanout_control`（Shutdown/Profiler/Admin 广播到 follower 工作队列）、`fanout_work`（把 payload 包成 `TPWorkMessage` 复制）、`fanout_abort`、`collect_admin_results`（并发收集每个 follower 的 AdminResult，op_id 校验）。
- `TPFollowerControlPlane`（follower 侧）：用 **multiprocessing Queue** 模拟 StageControlPlane 接口（`recv/recv_abort/send_admin_result`），底层 `run_in_executor` + 0.1s 轮询桥接进 asyncio。
- **谁需要 fanout 由调度器声明**：`Stage._execute` 只在 `scheduler.requires_tp_work_fanout=True` 时复制工作——`SimpleScheduler` 置 True（每 rank 都要跑同一函数喂 NCCL 集合通信），`OmniScheduler` 默认 False（工作从 entry rank 广播，走 SGLang 自己的 `broadcast_pyobj`）。

## 5.1 ModelWorker：进程的引导层（`model_runner/model_worker.py`）

每个引擎阶段进程内的执行引导，四步：`_init_model_config` → `_configure_backend_policy` → `_init_model_runner` → `_init_dllm_algorithm`。

### 架构投影：把多模态复合配置"翻译"给 SGLang

SGLang 只认单一 LLM 形状的 `hf_text_config`（层数/头数/hidden_size 用于内存规划与并行切分），而 Omni 模型的 HF config 是复合体（thinker_config / talker_config / language_config）。`_ARCH_CONFIG_MAP` 声明每个架构的投影路径：

| 架构 | 子配置属性 | text 配置属性 |
|---|---|---|
| `Qwen3OmniTalker` | talker_config | text_config |
| `Qwen3OmniThinkerForCausalLM` | thinker_config | text_config |
| `Qwen3ASRForConditionalGeneration` | thinker_config | text_config |
| `MossTTSDelaySGLangModel` / `MossTTSLocalSGLangModel` | language_config | —（自身即 text） |
| `Qwen3TTSTalker` | talker_config | — |
| `DotsTTSForConditionalGeneration` / `MingTTSSGLangModel` / `BailingMoeV2ForCausalLM` | llm_config | — |

`_apply_arch_override` 把子配置的字段**逐个抄写**到 `model_config.hf_text_config / num_attention_heads / num_key_value_heads / hidden_size / num_hidden_layers`。`WhisperForConditionalGeneration` 特判：encoder-decoder 形状（`d_model`、`decoder_layers`、注意力层数 ×2 编解码各一层）——投影不是无脑抄，每个架构有自己的形状语义。

### 后端策略

`_configure_backend_policy` 先应用 Omni 量化适配器，再按平台 + 架构 + 量化状态选 MoE/GEMM 后端。典型结论（FP8）：`Qwen3OmniTalker` FP8 时 MoE 与 dense GEMM 都压到 `cutlass`（triton FP8 内核不兼容），thinker FP8 只压 MoE、dense 保持 `auto`。**策略跟着内核兼容性走，不跟着性能直觉走。**

## 5.2 SGLModelRunner 与共置显存剖析（`model_runner/sglang_model_runner.py`）

### 模型注册

`_register_omni_model` 把 Omni 模型类注入 SGLang 全局 `ModelRegistry`，使 SGLang 能按 HF 架构字符串实例化它们——这是"Omni 模型跑在 SGLang 引擎上"的接线点。

### `_OmniKVCacheConfigurator`：三级 KV 余量剖析（本框架最硬核的数学）

上游 SGLang 的剖析逻辑：`可用 = 加载前空闲 − 加载后空闲`（全局空闲差）。**单引擎场景正确**；共置场景失效——另一个进程可能同时加载权重，全局空闲内存被别人吃掉，算出的 delta 偏小甚至为负。

Omni 的三级策略（`_profile_available_bytes`）：

```
无 total_gpu_memory_fraction 预算
   → 原样走上游全局 delta（非共置场景零行为变化）

有预算，NVML 能识别本进程内存
   → available = total_gpu_memory × fraction − process_used_bytes
   （NVML 精确到进程，最准）

有预算，NVML 不可用
   → stage load delta：pre_model_load vs post_model_load（SGLang 串行化初始化窗口内测量，
     此时无他进程并发加载，局部 delta 可信）
   → available = total × fraction − stage_load_bytes
```

每条路径都打结构化日志（`gpu_mem_accounting=nvml_process / stage_load_fallback` + 各字段的 GiB 值）——显存剖析出错是最难查的故障，日志把会计方法本身暴露出来。

一个只有源码注释才写得清的陷阱：配置类标着 `@dataclass(slots=True)`，dataclass 重建类对象会让零参 `super()` 的闭包单元指向重建前的类，所以这里 **`super()` 必须显式拼写参数**。这类 CPython 实现层知识不会出现在任何教程里。

## 5.3 ModelRunner 基类：异步解码状态机（`model_runner/base.py`）

### 同步路径 `execute()`：五步

```
_build_forward_batch → _prepare_and_forward → post_prefill/post_decode
→ _ensure_next_token_ids → _publish_next_tokens → _finalize
```

`_prepare_and_forward` 的 `is_lookahead` 形参区分普通步与前瞻步。

### 异步解码（one-step lookahead）的语义

动机：解码步的 GPU 前向 + 采样 + 收集是三段串行。把"收集"挪到下一步前向之后，GPU 与主机并行。实现分裂点在 **post-decode 边界**：

```python
@dataclass
class _PendingStep:
    event: ...            # launch 完成后立即 record 的设备事件
    launch_buf: ...       # post_decode_launch 的返回：设备侧快照 或 pinned host 暂存
    scheduler_output / forward_batch / schedule_batch / batch_result
```

**不变量：同时至多一个 `_PendingStep` 在飞**；句柄由**调用者**（OmniScheduler 的事件循环）持有而非 runner 持有——因为 launch-first 调度里第 N 步刚 launch、第 N−1 步还没 resolve，两个"当前批"短暂并存。

`execute_launch`（decode-only，`assert not is_prefill`）：

```
build → prepare_and_forward(is_lookahead=True)
→ post_decode_launch(...) → launch_buf        # 模型特化发布 resolve 所需载荷
→ ensure_next_token_ids → publish_next_tokens # GPU 侧 token 链条立即续上（FutureMap）
→ event = record_completion()                 # 事件此刻才"覆盖"已发布状态
→ resolve_batch = schedule_batch.copy()       # 绝不跨前瞻迭代持有可变活批！
```

`schedule_batch.copy()` 的原因注释写明："Never retain the mutable live ScheduleBatch across a lookahead iteration. The upstream overlap loop likewise queues batch.copy()."——活批会被下一轮调度改写，快照必须复制。

`execute_resolve`：

```
event.query() ?  _async_query_hit += 1        # 未阻塞即命中——前向足够长，收集提前完成
             :  event.synchronize(); _async_query_miss += 1
skip_rids = {已 finished / retracted 的请求}   # 滞后步的重复发射与重复 KV 释放都要防
post_decode_resolve(launch_buf, ...)          # 模型特化收集
_finalize(..., skip_rids=skip_rids)
```

`launch_buf` 的两种模型特化形态（`_PendingStep` docstring）：

- **device snapshot**（MOSS-TTS-Local）：正确性快照留在设备侧，无 host 拷贝——**不提供**主机重叠，只提供前向重叠；
- **pinned host staging**（Higgs）：launch 时异步主机拷贝填充固定缓冲——真正实现主机 D2H 与下一步前向重叠。

只有后者有 D2H 重叠；`event.query()` 证明的是"launch 步 GPU 工作已发布"，不是"主机拷贝已重叠"。观测计数器 `_async_query_hit/miss` 的注释专门澄清这一点——指标度量什么、不度量什么，写得清清楚楚。

### `_pinned_pingpong`：双固定缓冲防真竞争（全库最底层的一段）

```python
def _pinned_pingpong(self, bufs_attr, slot_attr, shape, dtype, *, realloc_on_grow):
    ... 两个 pin_memory=True 的 CPU 缓冲，按 slot 0/1 交替返回 ...
```

`_stage_token_ids` 在**采样时**就把 `next_token_ids` 异步拷进其中一个固定缓冲（`buf[:n].copy_(ids[:n], non_blocking=True)` + record event），后续 `.tolist()` 变成纯主机读。

为什么必须是**两个**？`_next_host_staging` 的 docstring 给出了教科书级解释：

> Two buffers are required: resolve(N) reads one on the host while launch(N+1)'s async host copy writes the other. **That CPU-read vs GPU-write overlap is not protected by single-stream ordering.**

CUDA stream 顺序只约束 GPU 操作之间的依赖；"CPU 读缓冲 A"与"GPU 异步写缓冲 B"之间没有 stream 序列化保护——单缓冲必然读写相撞。缓冲在 grow 时整对重分配，且旧缓冲由仍持有它的 resolve 快照保活，"replacement cannot alias an in-flight snapshot"。`realloc_on_grow` 模式按 shape/dtype 变化触发；`_token_id_host_bufs`（采样暂存）与 `_host_staging_buffers`（launch 暂存）是两套独立乒乓对。

### hook 点全景（子类如何介入）

`before_prefill / after前向 post_prefill / before_decode / post_decode / custom_prefill_forward / custom_decode_forward / post_decode_launch / post_decode_resolve / requested_capture_hidden_mode_* / lookahead_eligible`——基类把"一个 AR 步"拆成可覆写的阶段，模态特化全部发生在这些钩子里，主循环五个步骤永不改。

## 5.4 特化 Runner

### ThinkerModelRunner（`model_runner/thinker_model_runner.py`）

- **多模态嵌入注入**：`custom_prefill_forward` 把 image/video/audio 占位 token 位置替换为真实嵌入。占位位置用**提示词绝对坐标**（`_req_mm_token_positions`，CPU int64 张量缓存于 `req._omni_mm_positions`——"the merge never reads placement off a GPU mask"），分块预填充时 `_plan_modality_chunk` 按 `[prefix, prefix+length)` 窗口切片，`req._omni_consumed` 光标记录各模态已消费的嵌入数（分块续传不重不漏）。
- **Deepstack 特判**：无残余视觉嵌入时走 `forward_batch.input_embeds`（SGLang 原生通道）；有 Deepstack 残余时必须走自定义前向——注释："ForwardBatch cannot carry its residual embeddings"（ForwardBatch 结构装不下多层残余嵌入，只能闭包传递）。
- **`CaptureHiddenMode.NULL`**：thinker 的流式输出靠本地 forward hooks 抓隐藏态；SGLang 的 LAST 模式 hooks 会禁用 CUDA Graph 重放，所以两个阶段都强制 NULL——两个机制（抓取与图重放）冲突时，明确弃一保一。

### QwenTalkerModelRunner（`models/qwen3_omni/talker_model_runner.py`）

- **before_decode**：校验反馈/文本输入就绪（缺了直接 raise——"Talker decode reached model runner without ready feedback/text input"，把上游调度 bug 变成显式错误）、`prepare_decode_buffers` + 写反馈缓冲（音频反馈 + 文本 token 以 FIFO 驱动 AR 生成）。
- **post_prefill**：首层码本 token（`next_token_ids`）+ talker 隐藏态 → `code_predictor_forward` 生成码本 1–7 → 暂存 token → 发射码块与反馈。
- **post_decode**：`next_token_ids = self.model._sampled_token_ids[:bs].clone()`（talker 的采样已由预测器 CUDA Graph 完成，runner 只取结果）。

# 第六部分 端到端串讲：一次请求的完整生命周期

以"Qwen3-Omni 式" thinker → talker → code2wav（文本+语音双终端）为例，把五个框架串成一条线：

```
[HTTP]  POST /v1/chat/completions
   │ 构造 OmniRequest（inputs+params+metadata）
   ▼
[框架二·Coordinator.submit]
   max_in_flight 准入 → RoundRobin 选 talker 副本绑定 → 建 RequestInfo/future
   → PUSH SubmitMessage → entry_stage=thinker
   ▼
[框架二·Stage(thinker)]  control_plane.recv() 收到 Submit
   _execute → TP? leader fanout_work 给 followers（Simple 类型才需要）
   → inbox.put(IncomingMessage(new_request))
   ▼
[框架三·OmniScheduler(thinker) 线程]
   recv_requests → request_builder 线程池构建 → 准入预检 → waiting_queue
   → get_next_batch_to_run（SGLang 组合方法）→ get_new_batch_prefill（合并门）
   → run_batch → _run_batch
   ▼
[框架五·ThinkerModelRunner.execute]
   _build_forward_batch（ForwardBatch.init_new + CaptureHiddenMode.NULL）
   → custom_prefill_forward：占位 token → 嵌入注入（光标分块）
   → SGLang 前向 + 采样 → _stage_token_ids（固定内存乒乓暂存）
   → post_prefill：抓取隐藏态 → ModelRunnerOutput{outputs[rid], next_token_ids, host_token_ids}
   ▼
[框架三·OmniScheduler]  process_batch_result（上游 KV 回收/统计）
   → _emit_stream_output：outbox.put(stream 消息，隐藏态块)
   → outbox.put(result)
   ▼
[框架二·Stage(thinker)]  _drain_outbox
   stream → _send_stream_to_target("talker")：
       同 GPU 跨进程 → serialize_direct_cuda_ipc_stream_chunk（句柄+事件内联）
       → PUSH DataReadyMessage{chunk_id=0, data_ref}
   result → get_next=["talker"] → CUDA 张量 payload → direct ipc 或 relay
       → PUSH DataReadyMessage
   ▼
[框架二·Stage(talker)]  _schedule_receive_task（per-lane 保序）
   _on_data_ready → 读 relay/直通反序列化 → ack 成功（发送方 slot 归还）
   → input_handler.receive → _execute → inbox
   ▼
[框架三·OmniScheduler(talker) + 框架五·QwenTalkerModelRunner]
   before_decode：反馈缓冲写入（FIFO 消费音频反馈+文本）
   decode 步：launch(N) → resolve(N−1)（乒乓缓冲 + skip_rids）
   post_decode：_sampled_token_ids → 发射码块（流式）
   ▼
[框架二·Stage(talker)]  流块沿 stream_to=["code2wav"] 转发
[框架三·StreamingSimpleScheduler(code2wav/vocoder)]  on_stream_chunk 增量解码波形
   outbox stream → 终端无 target → _send_stream_to_coordinator → StreamMessage
   payload 完成 → send_complete(CompleteMessage)
   ▼
[框架二·Coordinator._handle_completion / _handle_stream]
   StreamMessage → 归一化逻辑名 → stream queue → HTTP SSE 音频帧
   双终端集齐 → merged = {text:…, audio:…} → future.set_result
   ▼
[HTTP]  响应完成；客户端断开 → stream() finally → coordinator.abort
   → PUB AbortMessage → 各 Stage._on_abort → scheduler.abort + 资源清算
```

这条线上的每一步，都能在上文找到对应的类、方法与设计理由。

# 第七部分 设计原则提炼

| # | 问题 | 机制（怎么做） | 代码位置 |
|---|---|---|---|
| 1 | 多模型拓扑各异，CLI 参数无法枚举 | 声明式 `PipelineConfig` + 点分覆盖 + patch 归一化 | `config/schema.py`、`config/sources.py` |
| 2 | 拓扑决策散落各处会漂移 | 启动时一次编译成三张计划，运行时零决策零校验 | `config/topology.py`、`pipeline/runtime_config.py` |
| 3 | 阶段拆进程会破坏进程内数据依赖 | `process_local_edges` 编译期锁死 | `topology.py`、`qwen3_tts/config.py` |
| 4 | 控制消息被大数据阻塞 | 双平面：ZMR+msgpack 信令 / Relay 大数据，`DataRef` 只传指针 | `control_plane.py`、`comm/engine.py` |
| 5 | 共享内存/IPC slot 泄漏导致边死锁 | ack 驱动回收 + abort 时**drain 后 ack** | `relay/shm.py`、`stage/runtime.py::_discard_data` |
| 6 | 流式块乱序损坏下游解码状态 | per-(request, source) 泳道前驱链保序 | `stage/runtime.py::_schedule_receive_task` |
| 7 | 多下游共享可变 payload 互踩 | 对象身份级容器隔离检查，共享则禁用本地直传 | `_is_isolated_projected_payload` |
| 8 | SGLang 上帝类绑死演进 | `__getattr__` 类级组合，状态自摆、方法外借 | `omni_scheduler.py` |
| 9 | 小请求 GPU 步开销占比过高 | 预填充合并门（最老请求 deadline 防饿死；TP 禁用防锁步失联） | `get_new_batch_prefill` |
| 10 | 解码步主机收集串行等待 GPU | 一步前瞻：launch/resolve 分裂 + CUDA Event | `base.py::execute_launch/resolve` |
| 11 | CPU 读与 GPU 异步写竞争同一缓冲 | 双 pinned 乒乓缓冲（单流顺序保护不了主机-设备竞争） | `base.py::_pinned_pingpong` |
| 12 | `.tolist()` 触发阻塞 pageable D2H | 采样即暂存固定内存，下游读纯主机 | `_stage_token_ids` |
| 13 | 共置时全局空闲差剖析 KV 失真 | 三级剖析：预算+NVML 进程内存 → 加载差 → 上游全局 | `_OmniKVCacheConfigurator` |
| 14 | GPU 拷贝发起后不可取消 | 取消先 shield 等内核停再传播；失败页保留到进程退 | `cuda_ipc.py`、`engine.py` |
| 15 | 客户端断开留孤儿请求占 GPU | stream 生成器 finally 自动 abort 广播 | `coordinator.py::stream` |
| 16 | 中止与完成天然竞态 | 完成时忽略未知请求；abort ID 有界集合吸收迟到消息 | `_handle_completion`、各调度器 |
| 17 | 调度器线程崩溃悬挂请求 | 崩溃经 `run_coroutine_threadsafe` 回 loop，逐请求 fail-fast | `stage/runtime.py::_handle_scheduler_crash` |
| 18 | 一阶段后台任务静默死亡 | 统一 done-callback 记录错误、停 loop、退出时上抛 | `_on_background_task_done` |
| 19 | 异步解码超跑多发流块破坏延迟码流 | skip_rids 纪律（finished/retracted/aborted 不再发射） | `omni_scheduler.py::_emit_stream_output` |
| 20 | 失败域模糊 | 失败域 = OS 进程；同进程多阶段共享命运，监控 5s 轮询 | `stage_workers.py::_run_process` |
